# DSH 部署

> **本目录全部内容均为非官方资料。** 由部署实践整理而成，**不属于** DeepSeek Harness
> 官方仓库的一部分，也不随官方发布、不承诺维护节奏。一切以仓库源码与官方文档为准。

## 目录定位

面向**企业内网 Linux 环境**部署 DSH 的落地资料：一份架构选型决策文档、一份**方案 B 的**
逐步执行手册、一份上机前的只读体检脚本。

DSH 处于 **pre-release** 阶段且明确声明「未来将出现破坏兼容性的变更」，因此本目录的
全部结论都**锚定在具体版本上**，并给出了复核方法——版本变化本身不会让文档失效，
**前提事实变化**才会。

## 快速开始

```bash
# ① 先读选型指南 §4.5「隔离强度决策」——这一步决定你的部署变体，不能跳过
# ② 在目标服务器上跑前置检查（只读，不修改任何系统状态）
bash 前置检查.sh
# ③ 无阻断项后，按执行手册 §2 在跳板机准备离线制品，从 §1 起按阶段顺序执行
```

`前置检查.sh` 的退出码：`0` = 无阻断项，`1` = 存在 FAIL（含「无法确定」类的保守判定）。
输出中 `FAIL` 必须解决、`WARN` 需逐条确认、`INFO` 仅作提示。

## 动手前必须知道的六件事

按踩坑概率排序，每条都在文档里有完整展开。

1. **反代必须传 `--trusted-host`。**
   不传的后果是「页面能打开、一发消息就失败」——`/api` 信任围栏会在认证之前返回 **403**。
   更坑的是：手册里 `curl -I` 返回 401 那条验收项**照样会通过**，容易被误判为部署成功。
   **验收必须用「真的发一条消息并收到回复」。**（指南 F2b / §5.2，手册 §7）

2. **先决定隔离档位，再动手。**
   「一人一实例」只买到**应用层**隔离；默认所有实例同一系统用户，**OS 层不隔离**。
   如果 agent 会接触不可信内容（外部邮件/网页/他人文档），必须叠加「按用户分 UID」或容器。
   参见指南 **§4.5**（含威胁模型两问与三档变体）。

3. **`glibc` 必须 ≥ 2.28。**
   推荐制品（`deepseek-harness-runtime-bin`，manylinux_2_28）以此为硬下限。
   用 `ldd --version` 确认；不满足就必须换路线（离线 npm 或自建容器）。

4. **进程打印的启动 URL 是 `http://127.0.0.1:<port>/`，不是公网域名。**
   抓 token 时按回环地址匹配，抓到后**手工改写成公网域名**再发给员工。另外 token 是
   **进程级、可重复兑换**的（不是一次性），等同密码——务必收紧 journal 读权限。

5. **配置不能靠 `profile.d` 之类的方式改。**
   DSH 的配置层只有：bundle patch → `$DSH_HOME/profiles/<name>/cordis.patch.yml` →
   `$DSH_HOME/cordis.patch.yml` → `--patch`。端口请用命令行 flag 给。

6. **`DSH_HOME` 强制非空。**
   控制台命令绝不回退 `~/.dsh`，缺失即退出码 2。每实例一个 `DSH_HOME`，由 systemd 注入。

## 部署制品选型（一句话版）

内网环境下推荐使用官方发布在 PyPI 的 **`deepseek-harness-runtime-bin`** 平台 wheel：
它是把 `dsh` CLI 与整棵 Node 依赖闭包打成的**单文件自包含可执行程序**，服务器侧
**不需要 Node / npm / pnpm / 任何构建工具链**（Linux x86_64 约 77MB，无 Python 依赖）。

| 方式 | 服务器需 Node/npm | 需构建工具链 | 需内网 npm 源 | 官方提供该制品 |
| --- | --- | --- | --- | --- |
| 上传源码，服务器构建 | 要 | 要 | 要 | — |
| 自建镜像 → 导入 → 容器启动 | 否 | 否 | 构建期要 | **否**（仓库零 Dockerfile/Helm） |
| **runtime wheel（推荐）** | **否** | **否** | **否** | **是** |

详见选型指南 §5.8（怎么做）与附录 D（是什么）。

## 维护方式：什么时候需要改文档

**版本号变化本身不会让文档失效，前提事实变化才会。**

DSH 发布新版本后，按选型指南 **§10** 的方法逐条复核 §2 的**前提事实清单（F1~F20）**：
到对应包的 README / 源码确认事实是否仍成立。某条失效时，引用它的章节（该表「影响」列
已标注）即需重写。每次复核后在指南的「复核记录」中追加一条。

最容易随版本漂移、需要优先复核的几条：**F2/F2b**（认证与信任围栏）、**F4**（会话格式
与写租约）、**F20**（会话格式代际与磁盘占用）、**F9**（产出取回通道）。
